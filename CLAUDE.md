## What this is

TenantGuard is a **specification-first, polyglot multitenancy framework** for regulated
environments (fintech, banking, insurance, SACCOs, government — primarily East Africa).
It provides tenant isolation, context propagation, and audit-event publishing (to a sibling
system called AuditForge). It was extracted from the CIC InsureMaster bancassurance platform.

## The spec is the source of truth

`core/spec.md` is authoritative. **All four language implementations must conform to it** —
same concepts, same guarantees, different syntax. Before implementing anything in a language
directory, read the spec and the matching per-interface doc in `core/` (`TenantContext.md`,
`TenantResolver.md`, `IsolationStrategy.md`, `AuditHook.md`, `PolicyHook.md`,
`ContextPropagator.md`). The core interfaces:

- **TenantContext** — immutable after creation (this is a hard security requirement, not a
  style choice: immutability is what prevents tenant-hopping mid-request). Carries tenant id,
  name, metadata, and a W3C trace id.
- **TenantResolver** — extracts tenant identity from a request (`X-Tenant-ID` header, JWT
  claim, subdomain, client cert, MQ header, or custom).
- **IsolationStrategy** — enforces data boundaries. Schema-based isolation is the **default
  and recommended** choice for regulated systems; Row-Level Security and Database-per-Tenant
  are the alternatives.
- **ContextPropagator** — carries tenant context across HTTP, async jobs, message queues,
  and threads using W3C Baggage + OpenTelemetry Trace Context.
- **AuditHook** — publishes structured `TenantEvent`s to AuditForge over an authenticated
  (signed) channel.

Non-negotiable invariants from the spec: validate tenant context on every request, reject
any attempt to switch tenants mid-request, and emit an audit event for every tenant-aware
operation.

## Repository layout

- `core/` — language-neutral spec, per-interface docs, JSON schemas (`core/schemas/`),
  lifecycle hook docs (`core/hooks/`)
- `java/`, `go/`, `python/`, `typescript/` — the four reference implementations, each with
  parallel submodules (`context`, `resolver`, `isolation`, `propagation`, `audit`,
  `compliance`, `policy`, `telemetry`, `middleware`)
- `sdk/` — thin per-language client SDKs
- `examples/` — framework-specific demos (Spring Boot, FastAPI, Gin, Express, Kafka, gRPC)
- `testkit/` — testcontainers helpers, integration/compliance/performance test suites
- `benchmarks/`, `tools/` (codegen, migration), `platform/` (docker/k8s/terraform),
  `ecosystem/` (AuditForge, PolicyForge, UI)
- `docs/` — architecture, concepts, security/compliance, ADRs, Mermaid diagrams

The parallel submodule naming across languages is intentional — keep it consistent when
adding code so the four implementations stay structurally mirrored.

## Build & test

Go is the reference implementation and the only wired-up CI (`.github/workflows/ci-go.yml`,
Go 1.23). Once Go code exists:

```bash
cd go/tenantguard && go test ./... -v      # matches CI; module lives here, not go/
cd go/tenantguard && go test ./context/    # single package
```

The Go module root is `go/tenantguard/` (module path `github.com/tenantguard/tenantguard`,
so imports read `github.com/tenantguard/tenantguard/context`). The package in `context/` is
named `tenantcontext` to avoid shadowing the standard-library `context` package.

Java (Maven, JDK 17+), Python (3.10+), and TypeScript build configs are present but empty —
populate `pom.xml` / `pyproject.toml` / `package.json` before their standard toolchains
(`mvn test`, `pytest`, `npm test`) will do anything.

## Roadmap context

v1.0 targets the core spec + Go reference implementation + Java/Python bindings, with
schema-based and row-level isolation, W3C trace propagation, and AuditForge integration.
TypeScript, a policy engine, and advanced isolation adapters come later (v1.1+). See
`ROADMAP.MD`.
